# Photo sync patterns for Iris

Research note, checked 2026-09-24. This records behavior stated in public first-party documentation. It does not claim to describe Google Photos or iCloud internals.

## Public product behavior

**Google Photos on Android.** Backup is opt-in and automatic after it is enabled, but Google says completion time depends on connection, upload size, and other conditions. Users can also start a manual backup for one or multiple items. Overall progress is shown as the number of items remaining; the library exposes preparing, backing up, complete, and paused states. Per-item indicators distinguish uploading, queued/paused, backed up, and permanent failure. Backup targets one Google Account at a time, and users can include or exclude device folders. These are useful queue and account-scoping precedents, not evidence of Google’s scheduling or persistence implementation. [Google Photos Help](https://support.google.com/photos/answer/6193313?co=GENIE.Platform%3DAndroid&hl=en)

Google Photos exposes mobile-data controls: a daily automatic-backup limit, a switch for videos over mobile data, roaming backup, and in some regions/operator plans unrestricted-data backup. Google notes that Android battery optimization can make Photos backup work poorly. Its help pages describe automatic backup but do not promise a particular background execution guarantee or explain how uploads resume at byte level. The same page lists backup limits of 200 MB or 200 MP per photo and 10 GB per video. [Google Photos Help](https://support.google.com/photos/answer/6193313?co=GENIE.Platform%3DAndroid&hl=en)

Those are consumer-app limits. The separate Google Photos Library API documents a 20 GB video upload limit; it is a developer API with a different upload flow and scope. See [Upload batching and multipart primitives](upload-batching-primitives.md) for its per-file byte transfer, resumable upload, and later item-creation batching, and for a comparison with object-store multipart upload. These public API rules do not reveal the Photos Android app's private transfer implementation. [Google Photos Help](https://support.google.com/photos/answer/6193313?co=GENIE.Platform%3DAndroid&hl=en) [Google Photos Library API: upload media](https://developers.google.com/photos/library/guides/upload-media)

**Apple iCloud Photos.** Apple says photos and videos upload automatically when iCloud Photos is enabled. Photos presents active-upload and paused indicators, a library status message, and the last sync time; in-progress or paused sync can also produce a library notification. Apple recommends power plus Wi-Fi and allowing sync to run overnight for large libraries, and notes that larger files can take longer. A priority option, Sync Immediately, prioritizes recently added items for the day, but may use more battery/cellular data and pauses in Low Power or Low Data Mode. [iPhone User Guide](https://support.apple.com/guide/iphone/sync-photos-videos-icloud-iph961b96c4d/27/ios/27) [Apple Support: paused sync](https://support.apple.com/en-us/101559)

Apple documents pauses for Low Data Mode, Low Power Mode, battery/system optimization, poor network, battery below 20%, overheating, and full iCloud storage. Some conditions resume automatically after a short wait or can be overridden with Sync Now; low battery calls for charging, overheating calls for cooling, and full storage requires freeing or upgrading storage. Apple advises against turning iCloud Photos off to troubleshoot a pause. This is evidence for communicating a reason and next step, not evidence that an app should copy Apple’s exact thresholds or override rules. [Apple Support: paused sync](https://support.apple.com/en-us/101559)

**Separate Apple developer API, not iCloud Photos internals.** PhotoKit's Background Resource Upload extension lets a third-party app queue uploads of photo-library resources to that app's server. Apple's guide says each `PHAssetResource` requires a separate upload job, the system schedules processing when network, power, and device conditions allow, and the extension must track processed resources and acknowledge finished jobs under an in-flight-job limit. The API supports the draft IETF resumable-upload protocol only when the server implements its capability checks and response headers. The guide identifies the newer extension on iOS 27 and an earlier API on iOS 26.1. This is a concrete Apple pattern for background resource upload, but it is not evidence about iCloud Photos' own implementation and does not directly match Iris's Android client or custom offset endpoint. [Apple Developer: background resource uploads](https://developer.apple.com/documentation/photokit/uploading-asset-resources-in-the-background)

## Android transfer guidance

Android’s current data-transfer guide names WorkManager for deferrable or background-initiated media uploads over the network, and says such work must tolerate interruption and deferral. WorkManager can constrain network type, charging, battery, and storage; if a constraint becomes unmet while work runs, it stops the worker and retries when the constraints are met. Retry uses configurable linear or exponential backoff. The documented retry mechanism schedules work again; Android’s guidance does not specify byte-level upload resumption. [Android: data-transfer options](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options) [Android: define work requests](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)

For user-started transfers where progress must remain visible and interruption would harm the experience, Android recommends considering a User-Initiated Data Transfer (UIDT) job; it starts immediately subject to constraints and system health, requires a notification, and is available from Android 14. The docs specifically require transfer state to survive a stop even if `onStopJob()` is not called and to be restored on a later start. WorkManager also supports long-running work through a foreground service and notification, but that path remains subject to foreground-service and job limits; Android’s guide points user-requested long transfers toward UIDT. Neither API defines Iris’s server protocol or guarantees that an HTTP upload can continue from a byte offset. [Android: data-transfer options](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options) [Android: UIDT jobs](https://developer.android.com/develop/background-work/background-tasks/uidt) [Android: long-running workers](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running)

JobScheduler also exposes estimated network bytes and a minimum network chunk estimate so the OS can decide when a transfer is likely to make progress. That setting describes expected network traffic that is difficult to pause or resume; it is a scheduling hint, not an upload chunking or resumability protocol. Details on the public batch and multipart primitives compared for Iris are in [Upload batching and multipart primitives](upload-batching-primitives.md). [Android: `JobInfo.Builder`](https://developer.android.com/reference/android/app/job/JobInfo.Builder#setMinimumNetworkChunkBytes(long))

## Implications for Iris

- Keep queue rows durable and account-scoped in the app database: persist the source URI/identity, upload ID, confirmed offset, and state before and after requests. On account switch, resume only jobs belonging to the selected account. Scheduler state alone is not the upload ledger.
- Use idempotent server upload IDs and server-confirmed offsets so a worker restart, lost response, or constraint change can safely retry the last chunk. Iris’s current [Android sync contract](../android-sync-contract.md) already specifies this pattern; Android’s scheduler documentation does not.
- Treat WorkManager as the default runner for automatic, interruptible background sync, with user-configurable network and charging preferences and a retry/backoff path. Consider UIDT for an explicitly user-started large transfer when continuous visible progress is a product requirement; its version and notification constraints should be accounted for. Do not promise an exact run time.
- Show both queue-level progress (remaining items and bytes) and item states such as queued, uploading, paused, backed up/processing, ready, and failed. Surface actionable pause causes where known (network policy, low battery, storage/auth failure), plus pause/resume controls. Google’s item states and count, and Apple’s reason-specific library status, support this UX pattern.
- Separate upload acceptance from later server processing. “Uploaded” should mean the server has acknowledged and verified the bytes; thumbnails/indexing can remain a distinct processing state, as in Iris’s existing sync design.

These are product and architecture implications drawn from the cited public behavior and Android API guidance. They do not assert undocumented Google Photos or iCloud internals.
