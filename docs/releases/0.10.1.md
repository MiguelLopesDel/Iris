# Iris 0.10.1

## Changes since 0.10.0

### Faster server start
- A model-free server no longer imports PyTorch at start; it is imported the
  first time a search or index operation needs it. Importing the server inside
  the image went from 16–19 s to under 2 s on a spinning disk, so restarts and
  updates come back sooner.

### Smaller updates
- The image no longer rebuilds its dependency layers for every new commit
  (`IRIS_COMMIT` moved after the installs in the `Dockerfile`). Until now each
  release replaced nearly the whole image, about 1.1 GB for CPU and 3.9 GB for
  CUDA, even when no dependency changed. From the next release on, an update
  that leaves the dependencies alone downloads only the changed code layers.
  Updating to 0.10.1 still downloads the full image once.
- Images built locally no longer copy personal or secret files from the
  checkout (`.release-keys/`, `*.jks`, `.iris.local`, the dev sandbox, a local
  Compose override).

### Development
- Staging runs the checkout's code mounted into the container and rebuilds the
  image only when the dependencies change: `./iris try` with a code change takes
  seconds instead of minutes. `./scripts/staging.sh update --rebuild` forces a
  build.
- CI runs the suite in parallel and the clean-install smoke alongside it.

## Deployment

Run `./scripts/server.sh update` from the production installation, or use
**Update now** under **Settings › Updates**. There is nothing else to do: no
migration and no reindexing.

The Android app has not changed since 0.10.0.

## Release validation

Staging ran this code before the tag. Checked there: the server comes up
healthy and the change is visible in the container. The full staging checklist
in `docs/process.md`, the `lab` app and a day of use were not done before
tagging. After deploying, run the post-update check from that document.
